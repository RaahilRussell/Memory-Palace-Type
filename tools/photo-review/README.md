# Photo comparison page

Open `http://127.0.0.1:5176/tools/photo-review/index.html` in the existing candidate Vite server. This standalone React page reads saved evidence only; it never posts a scene request, starts a service, runs inference, writes a registry, or controls either live viewer.

The page shows all 33 source photographs and any two selected implementations. Source / left 8 cm / right 8 cm select saved camera captures. Source-only overlay and swipe require the exact reference hash, recorded alignment and matching dimensions. Named source regions come from the research evaluator's masks; their thresholded bounds crop the same rectangle in each matched image. These diagnostic rectangles are not segmentation claims. Source metrics are hidden at offset views; a source photograph is not ground truth for an unseen side view.

URL state includes `photo`, `variants` (immutable record IDs), `view`, `mode`, `roi` and `mix`. Default aliases resolve once into content-specific IDs. Missing selected records stay visibly unavailable, rather than being replaced by a newer attempt. Changing the photo selects the standard two depth variants for that source. Browser back/forward and copy-link preserve the comparison.

## Read-only adapters

The tester-owned attempt registry may optionally declare `activeReportUrl`, matching only `^/\.local/photo-scene-candidate(?:-v\d+)?-results\.json$`. If absent or invalid, the original candidate report remains the default. A valid active report that is unavailable stays explicitly unavailable; it does not fall back to an older successful run. The current-renderer link derives its `report=candidate` or `report=candidate-vN` key from this field. `captureManifests: [{url, sha256}]` can add qualitative capture manifests without UI changes. Entries require the existing bounded evidence path and SHA-256 checks, are deduplicated by normalized URL with the pinned v1 entry, and are capped at 165 total requests including pinned entries. Conflicting hashes at an already pinned path are reported and ignored. Every loaded qualitative manifest still has to match its exact linked immutable implementation and source identity. The page never writes these registry fields.

- The pinned `/.local/candidate-album-scenes/capture-manifests/v1-photo01.json` adds five independent qualitative screenshot choices. Its manifest SHA and linked immutable implementation manifest SHA are verified before adaptation. Each choice retains its recorded Front, Side, Behind or timed movement label, and never occupies the calibrated `source`, `left` or `right` capture slots. Shared depth camera presets do not move these screenshots. They always disable overlays, swipe, ROI cropping and metrics. The original `.png` filenames and JPEG bytes remain unchanged; `actualMimeType: image/jpeg`, UI overlays and unmeasured extrinsics are displayed and preserved in provenance. New qualitative manifests must be explicitly pinned or added through a future verified capture registry; this page does not write them.

- `/.local/depth-fidelity-v1/manifest.json` plus per-case `captures/capture-report.json` and `evaluation-regions.json`. All files live in the original workspace and must be exposed through the root-owned bounded Vite evidence middleware. The precise labels are **Frozen surface · depth 256** and **Frozen surface · retained depth 384**. These are depth-only ablations on the same frozen renderer, not the full baseline or combined candidate. The flat photograph control is a separate variant.
- `/.local/photo-scene-variants/registry.json`, followed by immutable per-attempt manifests. Registry-declared manifest hashes are verified against response bytes. Scenes, textures, source images and GLBs do not count as clean renders. The adapter requires explicit `file.capture` metadata (`canvasOnly`, `view`, `width`, `height`, `alignmentVerified`, camera data) before rendering an archived file as a calibrated view. Current attempts without this evidence show **Render pending**, with archived provenance still accessible.
- Frozen `/.local/photo-scene-baseline/results-at-stop.json` and `visual-review-at-stop.json` are the baseline status and review authorities. `/.local/photo-scene-candidate-results.json` and `/api/memories` supply provisional candidate status and source upload URLs. Pending/failed/unavailable states are explicit. The baseline screenshot adapter deliberately does not equate a keyboard-driven side screenshot with a saved 8 cm camera preset. Offsets use estimated scene scale; they are not measured physical camera distances.

Each normalized variant is frozen in memory. Its metadata retains original source SHA, manifest SHA, code commit/dirty fingerprint where recorded, source-file/browser-bundle hashes, camera matrices, settings, model details, timings, file maps and unknowns. An absent code commit is displayed as unknown; a dirty file hash is not presented as a commit. Image hashes are recorded provenance, while the manifest byte hash is computed in the browser. No image integrity claim is made from a URL alone.

The comparison refreshes metadata every 30 seconds. It does not add new outputs to the tester or research registries. Those writers retain ownership of immutable snapshots and capture production. The live-viewer links open separate tabs on ports 5175 and 5176; camera synchronization with those applications is not implemented or claimed.

## Validation

`npx tsx --test tools/photo-review/model.test.ts`

`npx tsc --noEmit --target ES2022 --module ESNext --moduleResolution Bundler --jsx react-jsx --strict --esModuleInterop --resolveJsonModule --skipLibCheck tools/photo-review/review.tsx tools/photo-review/adapters.ts tools/photo-review/model.ts`

The focused checks cover immutable provenance, URL roundtrips, path containment, source-alignment gates, excluded coverage renders and failed/missing capture status. Browser layout and image loading need the root's running Vite instance and bounded evidence routes.
